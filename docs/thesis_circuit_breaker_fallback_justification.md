# การจัดการข้อมูลสูญหาย: เหตุใด Persistence (โมเดลสำรอง) จึงยังคงอยู่ใน Dynamic Routing

> ที่มา: ตอบ comment คณะกรรมการสอบข้อ 4 ("ควรทบทวนระเบียบวิธีในการจัดการข้อมูลสูญหาย โดยประยุกต์ใช้เทคนิคการเติมเต็มข้อมูล Data Imputation Techniques ที่เหมาะสมตามหลักการทางวิทยาการข้อมูล แทนการเลือกใช้โมเดลสำรอง") · โค้ดที่เกี่ยวข้อง: `app.py` (`select_model()`, `compute_neighbor_features()`) · ผลการวัด: `scripts/check_neighbor_staleness_sensitivity_clean.py`

## 1. ภาพรวม: ข้อมูลสูญหายมี 3 ลักษณะที่ต่างกัน

ระบบพยากรณ์ใช้ feature 2 กลุ่มที่อาจขาดหายได้อิสระจากกัน คือ (ก) ประวัติ PM2.5 ของสถานีเป้าหมายเอง และ (ข) ค่า/แนวโน้ม PM2.5 ของจังหวัดข้างเคียง (ใช้เป็น spatial feature) การ "ข้อมูลสูญหาย" ในแต่ละกลุ่มมีลักษณะต่างกันและต้องแก้ด้วยวิธีต่างกัน:

| ลักษณะข้อมูลสูญหาย | สาเหตุ | วิธีจัดการ |
|---|---|---|
| (ก) สถานีเป้าหมายเงียบ 2–48 ชั่วโมง | เซนเซอร์/การรายงานของสถานีนั้นขัดข้องชั่วคราว | **Data Imputation (H-lite)** — ดูรายละเอียดใน [docs/thesis_imputation_experiment.md](thesis_imputation_experiment.md) |
| (ข) ไม่มีจังหวัดข้างเคียงสักจังหวัดที่มีข้อมูลสด | หลายสถานีในภูมิภาคขัดข้องพร้อมกัน (มักเป็นปัญหาฝั่งผู้ให้บริการข้อมูล) | รายงานในเอกสารนี้ |
| (ค) ข้อมูลนำเข้าขาดหายรวมกันเกิน 30% ของ feature ทั้งหมด | ข้อมูลเสียหายเป็นวงกว้างผิดปกติ | Persistence (ไม่ได้ทดลองเพิ่มเติมในรอบนี้ เพราะเกิดน้อยมากและเสียหายกว้างเกินกว่าจะมีฐานข้อมูลสำหรับ impute) |

เอกสารนี้ตอบเฉพาะกรณี (ข) ซึ่งเป็นส่วนที่ยังไม่ได้ถูกแก้ด้วย H-lite (H-lite แก้เฉพาะกรณี (ก) เพราะเป็นคนละปัญหา: (ก) คือข้อมูลของสถานีเป้าหมายเองขาด ส่วน (ข) คือจังหวัดข้างเคียงที่ใช้เป็น feature เสริมไม่มีข้อมูล)

## 2. เหตุใดกรณี (ข) จึงยังใช้ Persistence เป็นทางเลือกสุดท้าย — วัดแล้ว ไม่ใช่ไม่ได้ลอง

### 2.1 ทดลองขยายเกณฑ์ "ความสดใหม่" ของข้อมูลเพื่อนบ้าน
ระบบกำหนดว่าเพื่อนบ้านต้อง "สด" (ข้อมูลล่าสุดห่างจากเวลาปัจจุบันไม่เกิน 3 ชั่วโมง) จึงจะนำมาคำนวณ feature ได้ตามปกติ คำถามคือ **ถ้าไม่มีเพื่อนบ้านที่สดเลย แต่มีเพื่อนบ้านที่ข้อมูล "เก่ากว่า 3 ชั่วโมงเล็กน้อย" จะยังนำมาใช้แทน Persistence ได้ไหม** — แทนที่จะปัดตกไปใช้โมเดลสำรองทันที

ทดลองด้วยวิธีเดียวกับที่ใช้ตัดสินใจ feature อื่นทุกตัวในงานนี้ (จำลองความไม่สดบนชุดทดสอบจริง ด้วยโมเดลที่ deploy จริง `_20260919_203455`, ข้อมูลที่แก้ปัญหาป้ายเวลาเพี้ยนแล้ว) เทียบ MAE กับ Persistence ที่เกณฑ์ตั้งไว้ก่อนดูผล: **ต้องดีกว่า Persistence อย่างน้อย 10%** (ใช้มาร์จิ้นกว้างกว่าการตัดสินใจ feature ปกติ เพราะนี่เป็นทางเลือกสำรองของทางเลือกสำรองอีกชั้นหนึ่ง)

### 2.2 ผลการวัด

| ข้อมูลเพื่อนบ้านเก่ากว่า | ดีกว่า Persistence (LightGBM / XGBoost) | ผ่านเกณฑ์ (≥10%) |
|---|---|---|
| 1–3 ชั่วโมง (= เกณฑ์ "สด" เดิม) | 10.7–11.6% | ผ่าน |
| 4 ชั่วโมง | 10.4% / 10.5% | ผ่าน (เฉียด) |
| 5 ชั่วโมง | 10.0% / 10.2% | ไม่ผ่าน (LightGBM) |
| 6 ชั่วโมง | 9.7% / 9.9% | ไม่ผ่าน |
| 12 ชั่วโมง | 7.9% / 8.5% | ไม่ผ่าน |
| 24 ชั่วโมง | 5.9% / 6.9% | ไม่ผ่าน |
| ไม่มีค่าเลย (NaN) | **−12.8% / −15.0% (แย่กว่า Persistence)** | ไม่ผ่านชัดเจน |

**ข้อสรุปจากการวัด**: ขอบเขตที่ข้อมูลเพื่อนบ้านยัง "คุ้มใช้แทน Persistence" อยู่ที่ประมาณ **4 ชั่วโมง** ซึ่งมากกว่าเกณฑ์ "สด" เดิม (3 ชั่วโมง) เพียง **1 ชั่วโมงเท่านั้น** — แคบเกินกว่าจะคุ้มค่าในการเพิ่มกลไกใหม่ (เงื่อนไขในโค้ด ชุดทดสอบ การแสดงผลหน้าเว็บ) เพื่อครอบคลุมเพียง 1 ชั่วโมงที่เพิ่มขึ้น ขณะที่สถานการณ์ "ไม่มีเพื่อนบ้านสดเลย" เองก็เกิดขึ้นน้อยมากอยู่แล้วในทางปฏิบัติ (จากการตรวจบันทึกการทำงานจริงของระบบ ไม่พบเหตุการณ์นี้เลยในช่วง 10 วันล่าสุด)

**ข้อสังเกตสำคัญ**: หากไม่มีข้อมูลเพื่อนบ้านเลย (ส่งค่าว่างเข้าโมเดลตรงๆ) ผลลัพธ์จะ**แย่กว่า Persistence อย่างมาก** (แย่กว่า 12.8–15.0%) ซึ่งยืนยันหลักการสำคัญทางวิทยาการข้อมูล: **การ impute โดยไม่มีข้อมูลอ้างอิงที่เกี่ยวข้องเลยไม่ใช่ทางเลือกที่ดีกว่าการใช้ Persistence** การป้อนค่าว่าง/ค่าที่ไม่มีมูลฐานเข้าโมเดลที่ไม่เคยเห็นลักษณะข้อมูลแบบนั้นตอนเทรน ทำให้พยากรณ์แย่ลงกว่าการไม่พยากรณ์อะไรเลย (คือใช้ค่าปัจจุบันคงที่)

## 3. ข้อสรุปเชิงหลักการที่ใช้ตอบ comment

คณะกรรมการแนะนำให้ประยุกต์ใช้เทคนิค Data Imputation **แทนการเลือกใช้โมเดลสำรอง** ซึ่งงานนี้ดำเนินการตามคำแนะนำดังกล่าวอย่างเป็นระบบ โดยแบ่งพิจารณาตามลักษณะของข้อมูลสูญหาย:

1. **เมื่อมีข้อมูลอ้างอิงที่เกี่ยวข้องให้ใช้ได้ (กรณี ก: สถานีเป้าหมายเงียบ)** — ใช้เทคนิค Data Imputation (H-lite) แทนโมเดลสำรองอย่างสมบูรณ์ ตามที่ comment ระบุ
2. **เมื่อไม่มีข้อมูลอ้างอิงใดให้ใช้เลย (กรณี ข: ไม่มีเพื่อนบ้านแม้แต่จังหวัดเดียวที่มีข้อมูลเพียงพอ)** — ทดลองแล้วพบว่าการขยายเกณฑ์เพื่อหลีกเลี่ยงโมเดลสำรองทำได้จำกัดมาก (1 ชั่วโมง) เนื่องจาก**ไม่มีฐานข้อมูลที่เกี่ยวข้องเพียงพอให้ impute อย่างน่าเชื่อถือ** การพยายาม impute ในสถานการณ์เช่นนี้ขัดกับหลักการพื้นฐานของเทคนิค Data Imputation เอง (ต้องมีข้อมูลที่สัมพันธ์กันเป็นฐานอ้างอิง ไม่ใช่การประมาณค่าจากความว่างเปล่า) จึงเลือกใช้ Persistence เป็นทางเลือกสุดท้ายซึ่ง**พิสูจน์ด้วยการทดลองแล้วว่าให้ผลดีกว่าทางเลือกอื่นที่ไม่มีมูลฐานรองรับ** (ดู ตารางข้อ 2.2 แถว NaN)

กล่าวโดยสรุป ระบบไม่ได้ "เลือกใช้โมเดลสำรองแทนการทำ Data Imputation" แต่ได้ประยุกต์ใช้เทคนิค Data Imputation อย่างเต็มที่ในทุกกรณีที่มีฐานข้อมูลรองรับ และคงโมเดลสำรองไว้เฉพาะในสถานการณ์พิเศษที่ไม่มีข้อมูลอ้างอิงใดให้ใช้เลย ซึ่งเป็นการตัดสินใจที่สนับสนุนด้วยผลการทดลองเชิงปริมาณ ไม่ใช่การเลือกใช้วิธีเดิมโดยไม่พิจารณาทางเลือกอื่น

## 4. ข้อจำกัด

- กรณี (ค) ข้อมูลขาดหายรวมเกิน 30% ของ feature ทั้งหมด ยังไม่ได้ทดลองหาทางเลือกอื่นแทน Persistence ในรอบนี้ (เกิดน้อยมากและข้อมูลเสียหายเป็นวงกว้างเกินกว่าจะมีฐานข้อมูลสำหรับ impute ได้อย่างน่าเชื่อถือ ตามหลักการเดียวกับข้อ 2)
- ผลการทดลองใช้ชุดทดสอบเดียว (ไม่ได้ทำ time-blocked cross-validation ครอบคลุมหลายฤดูกาลเหมือนการตัดสินใจ feature หลักของโมเดล) เนื่องจากเป็นการวัดเพื่อตัดสินใจเชิงนโยบายของกลไกสำรอง ไม่ใช่การเพิ่ม feature ใหม่เข้าโมเดล
- ความถี่ของเหตุการณ์ "ไม่มีเพื่อนบ้านสดเลย" ที่ตรวจพบ (0.6% สะสม, กระจุกตัวในเหตุการณ์เดียว) อ้างอิงจากข้อมูลการทำงานจริงช่วงเดือนกันยายน 2569 เท่านั้น อาจไม่ครอบคลุมทุกสถานการณ์ที่เป็นไปได้
